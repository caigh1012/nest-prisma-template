# Redis 连接与连接池说明

## 检查结论

当前项目没有配置 Redis 连接池。

`src/core/redis/redis.service.ts` 中只执行了一次 `new Redis(options)`，因此
`RedisService` 持有的是一个 ioredis 客户端实例。由于 `RedisService` 由全局
`RedisModule` 提供，NestJS 默认会将其作为单例复用，应用内普通 Redis 命令共用
该客户端的一条 TCP 连接。

以下导入仅用于引入客户端类和配置类型，不代表启用了连接池：

```ts
import Redis, { type RedisOptions } from 'ioredis';
```

## 当前连接配置

| 配置 | 当前值 | 作用 |
| --- | --- | --- |
| `host` | `REDIS_HOST`，默认 `192.168.1.203` | Redis 服务地址 |
| `port` | `REDIS_PORT`，默认 `6379` | Redis 服务端口 |
| `connectTimeout` | `30000` 毫秒 | 单次建立连接的超时时间 |
| `lazyConnect` | `true` | 创建客户端时不立即连接，由模块初始化阶段显式调用 `connect()` |
| `retryStrategy` | 最长等待 `2000` 毫秒 | 连接断开后的重连等待策略 |

`retryStrategy` 控制断线重连，不会创建或管理多条连接，因此不属于连接池配置。
未显式配置的 `maxRetriesPerRequest` 等选项采用 ioredis 默认值，它们同样只控制
命令重试或排队行为，不控制连接池大小。

## 为什么普通命令通常不需要连接池

ioredis 可以在同一条连接上连续发送和处理多个普通命令，NestJS 中复用单例客户端
通常已经能满足常规读写、Pipeline 和事务场景。数据库连接池中的 `min`、`max`、
空闲回收等概念不能直接套用到当前 ioredis 单机客户端。

盲目创建多个客户端还会增加 Redis 服务端连接数、应用资源占用和关闭连接时的
生命周期管理成本。因此，目前没有业务并发证据表明单连接成为瓶颈时，不建议仅为
“连接池”增加多个客户端。

## 需要额外连接的场景

以下功能会改变连接状态或长期占用连接，应创建并管理独立的 ioredis 客户端，而不应
与普通命令共用当前客户端：

- `SUBSCRIBE`、`PSUBSCRIBE` 等发布订阅命令；
- `BLPOP`、`BRPOP`、`XREAD BLOCK` 等阻塞命令；
- Redis Cluster 或 Sentinel 等需要专门拓扑配置的部署方式；
- 经压测确认单连接吞吐成为瓶颈，需要按明确规则拆分客户端的场景。

这类设计属于“专用连接”或“多个客户端实例”，并不是当前配置中已经存在的通用连接池。
新增时应同时定义创建数量、使用范围、错误监听、启动检查和应用关闭释放策略，避免连接
泄漏。关键 Redis 连接在应用启动阶段失败时，仍应抛出错误并终止启动。

## 当前建议

保留现有单例连接设计，不新增连接池参数。后续如果引入发布订阅或阻塞命令，应在
`RedisService` 中增加用途明确的独立客户端，并为每个客户端注册事件监听和关闭逻辑；
如果是性能扩容需求，应先通过监控和压测确认瓶颈，再决定客户端数量。
